# Периодические задачи на PostgreSQL: MVP

Дата: 13 октября 2026 года.

## 1. Решение

Каждая периодическая задача представлена одной строкой в PostgreSQL. Каждая пода проверяет возможность запуска примерно раз в минуту. Проверка расписания и захват выполняются одним атомарным запросом.

В MVP остаются **четыре столбца**, фиксированный срок блокировки **один час**, без heartbeat. Расписание, интервал проверки и таймауты хранятся в конфигурации Python. Блокировка относится к одному выполнению, а не ко всему циклу `while True`.

Это схема с допустимыми повторными попытками: она защищает захват и владение строкой, но не гарантирует единственное выполнение бизнес-действий после сбоев.

## 2. Таблица

```sql
CREATE TABLE periodic_tasks (
    name        text PRIMARY KEY,
    next_run_at timestamptz NOT NULL,
    locked_at   timestamptz,
    lock_token  uuid,

    CHECK ((locked_at IS NULL) = (lock_token IS NULL))
);
```

`CHECK` не добавляет столбцов: он запрещает несогласованное состояние, когда время блокировки есть, а владельца нет, или наоборот.

| Поле | Зачем нужно |
|---|---|
| `name` | Уникальное имя задачи, например `refresh_statistics` |
| `next_run_at` | Время запланированного запуска, который предстоит выполнить |
| `locked_at` | Время захвата; `NULL` означает отсутствие блокировки |
| `lock_token` | UUID конкретной попытки, позволяющий отличить старого владельца от нового |

Блокировка действует, пока `locked_at + LOCK_TIMEOUT > текущее время`.

`next_run_at` необходим независимо от блокировки. Если задача завершилась и сняла блокировку, он не позволяет другой поде сразу повторить уже завершённый запуск.

### Что перенесено из таблицы

| Ранее предложенное поле | Решение для MVP |
|---|---|
| `enabled` | Список активных задач задаётся конфигурацией приложения |
| `period` | Период или cron-расписание задаётся в Python |
| `retry_at` | Не используется: повтор разрешён после освобождения блокировки |
| `locked_by` | Имя поды, имя задачи и token записываются в логи |
| `last_success_at` | Успех и длительность записываются в логи/метрики |
| `lock_until` | Вычисляется из `locked_at` и общего таймаута |

Все поды должны использовать одинаковый таймаут блокировки. При разных значениях они будут по-разному трактовать одну строку. Изменение таймаута и расписания при rolling deployment требует согласования версий конфигурации.

## 3. Конфигурация Python

```python
from datetime import timedelta

POLL_INTERVAL = 60
LOCK_TIMEOUT = timedelta(hours=1)
MAX_RUNTIME_SECONDS = 45 * 60

# Пример: период от успешного завершения задачи.
TASK_PERIOD = timedelta(hours=1)
```

`LOCK_TIMEOUT` — через сколько другой исполнитель может перехватить строку. `MAX_RUNTIME_SECONDS` — локальный предел выполнения обработчика. Он должен быть меньше срока блокировки, с запасом на запросы БД, задержки и завершение отмены.

45 минут — пример настройки, а не универсальный предел. Если штатная работа может длиться больше часа, такой MVP нужно изменить: увеличить срок блокировки либо добавить продление.

## 4. Регистрация задачи

```sql
INSERT INTO periodic_tasks (name, next_run_at)
VALUES ($1, $2::timestamptz)
ON CONFLICT (name) DO NOTHING;
```

`$1` — имя; `$2` — время первого запланированного запуска.

Вставка выполняется при инициализации задачи. Несколько под могут безопасно делать её одновременно. При рестарте существующая строка не сбрасывается: расписание и блокировка сохраняются.

Не следует при каждом старте безусловно перезаписывать `next_run_at`, `locked_at` или `lock_token`.

## 5. Атомарный захват

```sql
UPDATE periodic_tasks
SET
    locked_at = clock_timestamp(),
    lock_token = $2::uuid
WHERE name = $1
  AND next_run_at <= clock_timestamp()
  AND (
      locked_at IS NULL
      OR locked_at + $3::interval <= clock_timestamp()
  )
RETURNING name, next_run_at, locked_at, lock_token;
```

Параметры:

- `$1` — имя задачи;
- `$2` — новый `uuid.uuid4()` для этой попытки;
- `$3` — `LOCK_TIMEOUT`, передаваемый в asyncpg как `timedelta`.

Вернулась строка — можно выполнять задачу. Не вернулась — задача ещё не должна запускаться или принадлежит другому исполнителю.

Запрещён вариант «сначала прочитать, что свободна, затем безусловно обновить»: между этими действиями задачу может забрать другая пода.

При конкурентных `UPDATE` одной строки и уровне `READ COMMITTED` PostgreSQL после ожидания проверяет `WHERE` на обновлённой версии строки. Поэтому конкурент увидит установленную блокировку и не захватит задачу. Для этой операции отдельный `SELECT FOR UPDATE` или `SERIALIZABLE` не требуется. [1]

**Захват должен быть закоммичен до вызова обработчика.** Транзакция захвата не остаётся открытой на время бизнес-логики. Иначе row lock помешает другим исполнителям перехватывать задачу, даже когда прикладной таймаут истёк. [2]

Отдельный процесс очистки просроченных блокировок не нужен: захват сразу заменяет старые `locked_at` и `lock_token`.

Время проверяется по часам БД. `clock_timestamp()` возвращает фактическое текущее время; `now()` — время начала транзакции. [3]

## 6. Успешное завершение

Для MVP выбираем расписание **от успешного завершения**. Период хранится в Python и передаётся параметром:

```sql
UPDATE periodic_tasks
SET
    next_run_at = clock_timestamp() + $3::interval,
    locked_at = NULL,
    lock_token = NULL
WHERE name = $1
  AND lock_token = $2::uuid
  AND locked_at + $4::interval > clock_timestamp()
RETURNING name, next_run_at;
```

- `$1` — имя задачи;
- `$2` — token полученного захвата;
- `$3` — период задачи;
- `$4` — `LOCK_TIMEOUT`.

Если задача завершилась в 12:07 и период равен часу, следующий запуск будет запланирован на 13:07. Проверка раз в минуту добавляет задержку обнаружения, поэтому это не гарантия запуска ровно в 13:07.

Следующее время и освобождение обновляются одной операцией: между ними нет окна для повторного захвата старого запуска.

Если запрос ничего не вернул, блокировка истекла или сменился владелец. Нельзя записывать успех и менять расписание от имени старого исполнителя.

Если нужны запуски строго по часам или cron, меняется вычисление следующего `next_run_at`. В этом случае приложение передаёт рассчитанный timestamp вместо периода. Нужно отдельно определить политику пропущенных запусков и часовой пояс расписания.

## 7. Ошибка выполнения

После остановки неудачного обработчика освободить только собственную блокировку:

```sql
UPDATE periodic_tasks
SET locked_at = NULL, lock_token = NULL
WHERE name = $1
  AND lock_token = $2::uuid
RETURNING name;
```

`next_run_at` не меняется: повтор относится к тому же запланированному запуску.

Следующая проверка любой поды может повторно захватить задачу. **Это не глобальная задержка на минуту после ошибки:** другая пода может проверить строку уже через секунду. В MVP нет общего retry-backoff и ограничения числа попыток. Для постоянно падающих задач это может привести к частым повторам.

Если освобождение не удалось из-за ошибки БД, записать ошибку в лог и оставить восстановление истечению блокировки.

Не снимать блокировку, пока обработчик или запущенные им фоновые операции ещё продолжаются. При отмене процесса, когда безопасная остановка не подтверждена, консервативный вариант — оставить строку до истечения срока блокировки.

## 8. Зачем оставлен lock_token

Пример:

1. Пода A захватила задачу с token A.
2. Через час блокировка истекла.
3. Пода B захватила задачу с token B.
4. Старый обработчик A завершился и попытался освободить строку.

Условие `WHERE name = $1 AND lock_token = $2` не позволит A очистить блокировку B или изменить её расписание.

Имя поды не заменяет token: на одной поде могут быть разные процессы и последовательные попытки. UUID создаётся заново для каждого захвата.

## 9. Каркас Python

Если в проекте уже есть SQLAlchemy, можно использовать его. Для отдельного небольшого компонента подходит `asyncpg` с пулом. Соединение берётся только на короткую операцию с БД и возвращается в пул до выполнения обработчика. В asyncpg отдельный запрос вне явной транзакции работает в auto-commit. [4]

Репозиторий содержит четыре метода:

| Метод | Реализация |
|---|---|
| `register(name, first_run_at)` | SQL из раздела 4 |
| `try_acquire(name, token, lock_timeout)` | SQL из раздела 5; возвращает запись или `None` |
| `complete(name, token, period, lock_timeout)` | SQL из раздела 6; возвращает признак обновления |
| `release(name, token)` | SQL из раздела 7; возвращает признак обновления |

Ниже каркас для Python 3.11+, а не самостоятельный модуль: реализация `repo`, создание пула и обработчик зависят от проекта. Запись из `try_acquire` имеет доступ по ключам, как `asyncpg.Record`.

```python
import asyncio
import logging
import random
import uuid
from datetime import timedelta

logger = logging.getLogger(__name__)

POLL_INTERVAL = 60
LOCK_TIMEOUT = timedelta(hours=1)
MAX_RUNTIME_SECONDS = 45 * 60


async def execute_claimed(repo, task, handler, period):
    name = task["name"]
    token = task["lock_token"]

    try:
        async with asyncio.timeout(MAX_RUNTIME_SECONDS):
            await handler(scheduled_for=task["next_run_at"])
    except asyncio.CancelledError:
        # При остановке процесса оставляем восстановление таймауту.
        raise
    except Exception:
        logger.exception("Task failed: name=%s token=%s", name, token)
        # Допустимо, если handler уже прекратил все свои действия.
        await repo.release(name=name, token=token)
        return

    # Ошибка записи успеха не переводится в безусловное освобождение.
    # Результат мог быть выполнен, а исход COMMIT может быть неизвестен.
    completed = await repo.complete(
        name=name,
        token=token,
        period=period,
        lock_timeout=LOCK_TIMEOUT,
    )

    if not completed:
        logger.error("Lease lost: name=%s token=%s", name, token)


async def run_periodic(repo, name, handler, period):
    while True:
        try:
            task = await repo.try_acquire(
                name=name,
                token=uuid.uuid4(),
                lock_timeout=LOCK_TIMEOUT,
            )

            if task is not None:
                await execute_claimed(repo, task, handler, period)
        except asyncio.CancelledError:
            raise
        except Exception:
            logger.exception("Runner error: name=%s", name)

        await asyncio.sleep(POLL_INTERVAL + random.uniform(0, 5))
```

Для каждой задачи — отдельная coroutine, чтобы длительное выполнение одной не блокировало проверку остальных. Число одновременно выполняемых задач нужно ограничивать при необходимости.

В этом каркасе сон начинается после завершения предыдущей итерации. Он не обеспечивает точный минутный тик. При ошибках БД повтор выполняется примерно через минуту с небольшим jitter. Запросам БД и получению соединения из пула также нужны ограниченные таймауты, задаваемые в репозитории/драйвере.

`asyncio.timeout()` отменяет coroutine, но обработчик должен реагировать на отмену и не подавлять `CancelledError`. Блокирующий код, продолжающийся поток или внешний запрос не обязательно остановятся вместе с отменой ожидания. Поэтому этот механизм уменьшает вероятность пересечения исполнителей, но не гарантирует её отсутствие. [5]

Если используется SQLAlchemy, конкурентные задачи должны иметь отдельные `AsyncSession`. [6]

## 10. Оставшиеся риски MVP

### Пересечение после часа

Истечение блокировки не останавливает старый процесс. Другой исполнитель может начать работу одновременно с ним. Token защищает служебную строку, но не внешние бизнес-действия. Если пересечение недопустимо, нужен дополнительный механизм защиты результатов, а не только этот MVP.

### Повторные побочные эффекты

Пода могла выполнить действие и умереть до записи успеха. Повторная попытка выполнит то же действие ещё раз. Обработчик должен допускать безопасный повтор.

Логический ключ идемпотентности одного запланированного запуска:

```python
idempotency_key = (task["name"], task["next_run_at"])
```

Для внешнего API преобразовать его в стабильную строку с согласованным форматом timestamp. Использовать его только там, где получатель действительно поддерживает дедупликацию. Token захвата не подходит: он меняется при повторах. [7]

Для строгой защиты изменений в том же Postgres можно проверять владение и записывать бизнес-результат в одной короткой транзакции, блокирующей строку задачи. Для внешнего получателя возможен fencing token, но MVP такого механизма не содержит.

### Недоступность БД и неизвестный исход запроса

Без подтверждённого захвата новые задачи не запускаются. Если захват закоммитился, но ответ потерян, задача не выполняется этой подой и будет доступна после истечения блокировки.

Активная задача в варианте без heartbeat автоматически не обнаружит потерю БД. Она может продолжить бизнес-работу, а запись успеха не удастся. Следующий исполнитель может повторить действие. Нельзя трактовать ошибку записи успеха как доказательство, что бизнес-действие не произошло.

При асинхронной репликации failover может потерять подтверждённые записи захвата или успеха. Нужно проверить гарантии используемого кластера. [8]

### Медленное восстановление и частые ошибки

После падения ждать до часа, плюс задержку очередной проверки. После освобождения неудачного запуска общего backoff нет; возможна серия быстрых повторов разными подами.

### Пропущенные запуски

Для выбранной политики выполняется один текущий просроченный запуск, а после успеха следующий назначается от завершения. Все пропущенные интервалы отдельно не воспроизводятся. Это подходит, например, для обновления актуального состояния; для обработки каждого временного окна потребуется другая политика или таблица запусков.

## 11. Минимальная проверка перед внедрением

1. Одновременно попытаться захватить одну строку из нескольких соединений: при действующей блокировке успешный захват должен быть один.
2. Остановить исполнителя после захвата: повторный захват возможен только после истечения срока.
3. Перехватить просроченную задачу новым token и попытаться завершить/освободить её со старым: строка не должна измениться.
4. Успешно завершить задачу и убедиться, что до `next_run_at` новый захват невозможен.
5. Вызвать ошибку обработчика: `next_run_at` сохраняется, собственная блокировка снимается.
6. Имитировать потерю ответа на запись успеха и проверить безопасный повтор бизнес-действия.
7. Проверить отмену обработчика и отсутствие продолжающихся фоновых действий перед ранним освобождением.
